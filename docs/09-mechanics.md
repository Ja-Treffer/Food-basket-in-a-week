# 09 · 结算机制（实现口径）

学生看到的是「怎么玩」那十行大白话；这里写的是**代码里到底怎么算的**。
两套说法必须一致 —— 改这里就同步改 `showRules()`，反之亦然。

## 一天的结算顺序

```
1. 今日情景（EVENTS）        不归因于玩家，先记一笔
2. 逐任务逐笔（TASKS/LONG）  按当天任务顺序，每步一条
   └ 没做/跳过的任务        记一条 skip，口味 −5
3. 延迟后果（pending）       只取 day == 今天 的那些
4. 接受度崩盘检查            c < 25 时触发
5. 倡导（仅末日）            35% 判定
6. 回弹（仅末日结算后）      正的 m 按 0.60 入池
7. 夹到 0–100，写入 book
```

## 抽值

选项给的是区间 `fx = {p:[min,max], s:[…], c:[…], m:[…]}`。
结算时**每个轴各自**在区间里均匀取整数（`rng.randi_range(min, max)`）。
缺哪个轴就记 0。区间的宽度表示「这件事本身取决于条件」，不是误差棒。

## 截断与对账

读数钳在 0–100，但每笔账记的是**截断之后的实际变化**（`before / after`），
所以「起值 + Σ实际变化 = 止值」永远成立 —— 这条是可对账的硬约束（selftest AC-02）。

## 出去补一顿（崩盘）

- 触发：`c < 25`
- 动作：把**最近 3 笔环境改善**（负的 `p`）的绝对值回吐 **55%** 到 `p`；`c` 拉回 **32**
- 上限：每局最多 **2 次**
- 教学含义：把口味压到家人吃不下去，省下来的环境收益会被还回去

## 回弹（rebound）

- 每笔**正的** `m` 按 **0.60** 入池
- 末日结算时乘 **0.80**；若当天是网购节再 **+0.20**
- 上限 **16** 格（换算成 `p` 的负担）
- 教学含义：省钱不等于减排，省下来的钱会去别处消费

## 延迟后果

两种写法，结算时统一换算成绝对日：

| 写法 | 含义 |
|---|---|
| `{"delay": {"after": 2}}` | 从今天起第 2 天 |
| `{"delay": {"day": 5}}` | 第 5 天（绝对） |

都会 `min(days, at)` 封顶，所以第 7 天做的中期任务不会推到第 8 天。
普通任务用 `after: 2`；中期任务 `after: 2~3`。

## 倡导（向学校提议）

- 不直接改读数
- 只在末日判定，成功率 `base = 0.35`，按当前 `c` 微调（高 +0.15 / 低 −0.15），有政策条目再 +0.20
- 成功：`p` 减 8–14；失败：0

## 自定做法（DIY）

- 玩家自己写的一句话，**不计入任何读数**
- 结算时记一条 `kind: "diy"`，标「需自行举证」
- 理由：未经核校的数值不由系统代填

## 跳过

- 没做，或点了「就这样过一天」
- 记一条 `kind: "skip"`，`c −5`
- 跳过也是一个选择，同样进账单

## 课堂时钟

- 默认 300 秒（`CFG.timeBudget`），`?minutes=7` 改，`?timer=0` 关
- 到点就地结算当天，并把「进入下一日」改成「直接看总结算」
- 提前结束时逐日复盘只列已走过的天数（`book.length`），不是写死 7
